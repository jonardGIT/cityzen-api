1. EXECUTIVE SUMMARY
================================================================================

Architecture: Express + TypeScript + Prisma (PostgreSQL)
Auth: Dual-mode JWT (local app-jwt / Supabase-jwt), MFA (local-totp / Supabase-totp)
Role Model: 9 roles in Philippine LGU hierarchy (NATIONAL_ADMIN > REGIONAL_DIRECTOR
            > PROVINCIAL_ADMIN > CITY_ADMIN > DISPATCHER > RESPONDER > CITIZEN_REPORTER
            + lateral AUDITOR + CITY_CONTENT_EDITOR)
Routes: 21 route files, ~80+ endpoints
Feature Flags: FEATURE_AUTH_PROVIDER, FEATURE_TOKEN_MODE, FEATURE_MFA_MODE,
               FEATURE_MEDIA_STORAGE, FEATURE_RECORD_DELETION

Overall Assessment: The API is well-structured with consistent patterns. The CRUD
factory engine provides good uniformity. However, there are several validation
inconsistencies, scope enforcement gaps, and error format divergences that need
attention. The most critical issues are in the assignments controller (missing
jurisdiction scope enforcement) and UUID validation inconsistencies.

2.2  USERS ROUTES — /api/v1/users/*
--------------------------------------------------------------------------------

  Route:     GET /api/v1/users/capabilities
  Expected:  Return role capabilities for authenticated user. Any role allowed.
  API State: Requires JWT only (no role restriction). Returns role profile
             metadata including permissions, scope, canUpdateUser, canDeleteUser.
  Mismatch:  NONE — Correctly accessible to all authenticated users.

  ----

  Route:     GET /api/v1/users
  Expected:  List users visible to admin. Jurisdiction-scoped.
  API State: Requires JWT + ADMIN_ROLES (CITY_ADMIN+). Applies jurisdiction
             scope filtering. Supports pagination + archive scope.
  Mismatch:  NONE

  ----

  Route:     GET /api/v1/users/:id
  Expected:  Get user by ID. Admin only. Jurisdiction-scoped.
  API State: Requires JWT + ADMIN_ROLES. Validates UUID via controller regex.
             Checks canReadUserRecord() for jurisdiction scope.
  Mismatch:  ISSUE — Controller uses UUID_REGEX which accepts UUID versions 1-8.
             The route-level validator (from bodyValidators) uses .isUUID() which
             also accepts any version. These are now consistent (both broad).
             However, the :id param has NO route-level UUID validator. UUID
             validation happens only in the controller's getUserId() function.
  Suggested: Add param('id').isUUID() to the route definition for consistency
             with other routes that use incidentTimelineParamValidator.

  ----

  Route:     POST /api/v1/users
  Expected:  Create user. Admin only. Validate body fields.
  API State: Route applies createUserValidator (name, email, password strength,
             role enum, jurisdictionType/jurisdictionId pair). Controller
             duplicates name/email/password presence check (422 vs 400).
  Mismatch:  ISSUE — Duplicate validation between route validator and controller:
             - Route validator: password 12+ chars with regex pattern → 400
             - Controller: name/email/password presence → 422
             - Route validator runs first. If it passes, controller checks pass.
             - But if route validator fails, it returns 400 with {message:
               'Validation failed', errors: [...]} format.
             - Controller failures return 422 with {message: '...'} format.
             The status code difference (400 vs 422) creates ambiguity.
  Suggested: Remove the controller's redundant field-presence checks and rely
             solely on the route validator. Or standardize both to the same
             status code.

  ----

  Route:     PATCH /api/v1/users/:id
  Expected:  Update user. Admin only. Enforce hierarchy rules.
  API State: Route applies updateUserValidator. Controller enforces hierarchy:
             canManageRole(), self-update restrictions, jurisdiction scope.
  Mismatch:  SAME STATUS CODE ISSUE — Route validator returns 400, controller
             returns 422 for similar validation failures. No :id param
             validator at route level.

  ----

  Route:     DELETE /api/v1/users/:id
  Expected:  Delete/archive user. Admin only. Prevent self-deletion.
  API State: Requires JWT + ADMIN_ROLES. Prevents self-deletion. Checks
             canManageRole() + canReadUserRecord() for scope. Revokes sessions.
  Mismatch:  NONE — No :id param validator but handled in controller.

  ----

  Route:     POST /api/v1/users/:id/restore
  Expected:  Restore archived user. Feature-gated (archive mode).
  API State: Conditionally registered via isArchiveEnabled(). Checks hierarchy
             and scope.
  Mismatch:  NONE

             controller should check isArchiveEnabled() and return 409 if
             disabled, but this check may be missing.
  Suggested: Gate restore registration behind isArchiveEnabled() or add a
             controller-level check.

3. CROSS-CUTTING FINDINGS

3.1  UUID VALIDATION INCONSISTENCY
     ─────────────────────────────
     Location:    Multiple controllers and validators
     Severity:    MEDIUM

     The codebase has three different UUID validation approaches:

     a) usersController.ts — UUID_REGEX:
        /^[0-9a-f]{8}-[0-9a-f]{4}-[1-8][0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$/i
        Accepts versions 1-8, requires RFC variant bits [89ab].

     b) assignmentsController.ts — UUID_REGEX:
        /^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i
        Accepts ANY format matching the UUID structure (no version/variant check).

     c) bodyValidators.ts — express-validator .isUUID() (no version):
        Accepts any UUID version recognized by the validator library.

     d) incidentTrustValidators.ts — express-validator .isUUID():
        Same as (c).

     e) incidentEscalations / mutualAidRequests routes — .isUUID():
        Same as (c).

     Recommendation: Standardize on .isUUID() (no version) at the route level
     for all :id params and body UUID fields. Remove controller-level UUID
     regex checks that duplicate route validation. The broad .isUUID() approach
     is the correct choice since PostgreSQL gen_random_uuid() produces v4 UUIDs
     but Prisma @default(uuid()) may produce others in edge cases.


3.2  ERROR RESPONSE FORMAT INCONSISTENCY
     ────────────────────────────────────
     Location:    All controllers
     Severity:    LOW-MEDIUM

     Three distinct error response shapes exist:

     a) Validation middleware (validateRequest):
        Status 400: { message: 'Validation failed', errors: [{ field, message }] }

     b) Controller-level validation:
        Status 422: { message: 'specific error message' }

     c) Special flags in auth responses:
        { message: '...', mfaRequired: true }
        { message: '...', emailConfirmationRequired: true }
        { message: '...', mfaEnrollmentRequired: true }

     d) mutualAidRequests structured validation:
        { message: 'Validation failed', errors: [{ field, message }] }

     e) Global error handler:
        { message: 'Internal server error' } (500)
        { message: 'Conflict: resource is still referenced...' } (409)

     Recommendation: Document the error response contract. Consider evolving
     all error responses to a standard envelope:
        { message: string, errors?: Array<{field, message}>, metadata?: object }


3.3  PARAM :id VALIDATION GAPS
     ──────────────────────────
     Location:    Multiple routes
     Severity:    MEDIUM

     Routes that validate :id as UUID at route level:
       ✓ GET /incidents/:id/timeline (via incidentTimelineParamValidator)
       ✓ GET /incidents/audit/:id/timeline
       ✓ GET/PATCH/DELETE /incident-escalations/:id
       ✓ GET/PATCH/DELETE /mutual-aid-requests/:id

     Routes that do NOT validate :id at route level:
       ✗ GET/PATCH/DELETE /users/:id
       ✗ GET/PATCH/DELETE /incidents/:id
       ✗ GET /incidents/audit/:id
       ✗ GET /incidents/:id/media/:mediaId
       ✗ GET/PATCH/DELETE /assignments/:id
       ✗ DELETE /auth/sessions/:id
       ✗ GET /audit-logs/:id
       ✗ All CRUD factory routes (/:id on all resource types)

     For CRUD factory routes, the getParamId() utility handles validation.
     For custom routes, some controllers validate in-handler (usersController
     getUserId), others don't (auth sessions).

     Recommendation: Add param('id').isUUID() to the CRUD factory's
     GET/:id, PATCH/:id, DELETE/:id, POST/:id/restore routes. This provides
     uniform 400 responses for malformed IDs before hitting the database.
