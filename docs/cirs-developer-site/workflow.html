Repository Workflow

Start from the owning abstraction, not from broad search.

The main implementation surfaces are already split by concern. Work from the nearest controller, route, service, middleware, utility, or CRUD factory instead of spreading logic across the repo.

First routing choice Find the owning layer

Pick the nearest controller, route, service, middleware, factory, or schema file that actually decides the behavior.

Most useful habit Validate immediately

After the first real edit, run the narrowest test or build check that can prove or disprove the change.

Repository posture Generic where valid, custom where needed

Standard resources belong in the CRUD engine, but incident and privacy-heavy flows need explicit custom logic.

Main Surfaces

Controllers

Own request handlers and custom endpoint behavior.

Routes

Own Express wiring and auth or role boundaries.

Services

Own reusable domain logic and provider integration.

Middleware

Own auth, rate limiting, audit, and error behavior.

Engine

Own standard CRUD behavior through controller, route, and validator factories.

Prisma

Own schema shape, relations, and migration alignment.

Repository Matrix

Surface What it owns Use it when
src/controllers Request handlers and custom endpoint logic The behavior is computed in the handler itself
src/routes Route mounting, middleware composition, access boundaries You need to change URL wiring or auth boundaries
src/services Reusable business logic and provider integration Multiple handlers need the same domain logic
src/middleware Auth, audit, rate limiting, request safety, and errors The behavior applies across many endpoints
src/engine Standard CRUD controller, route, and validator factories The resource is conventional and should stay generic
prisma and SQL scripts Schema shape, constraints, indexes, migration rollout Data model or archive behavior changes

Practical Rules

  • Use the CRUD factory for conventional resources instead of hand-rolling standard handlers.
  • Keep incident-specific behavior in custom logic when the domain goes beyond generic CRUD.
  • Preserve archive-safe behavior and avoid hard-delete assumptions.
  • Scope access by the narrowest valid jurisdiction and fail closed when boundaries are unclear.
  • Keep Prisma schema, SQL migrations, and runtime behavior aligned.

Validation

After a meaningful backend change, prefer the narrowest executable check that can falsify the change: a focused Jest or Supertest run, a targeted type check, or a build command for the touched slice.

Step 1 Change the smallest owning slice first
Step 2 Run the narrowest relevant validation immediately
Step 3 Only widen scope after the first check passes or redirects you

Validation Matrix

Change type First validation to prefer Why
Controller or route behavior Focused Jest or Supertest slice Falsifies the request and response path directly
Type or contract changes Narrow type check or build step Shows whether the code still compiles across the touched boundary
Schema or migration change Prisma generate plus the narrowest schema-aware check Confirms runtime types and migration assumptions still align
Docs or config only Diagnostics or targeted diff review There may be no narrower executable behavior to run

Safe Developer Routine

  1. Identify the owning surface from the request or failing behavior.
  2. Read only enough nearby code to form one local hypothesis.
  3. Make the smallest edit that tests that hypothesis.
  4. Run focused validation before expanding the change.
  5. Keep docs, schema, or config in sync when the behavior surface changed.

Most wasted time in this repo comes from debugging the wrong layer. Start from the code that actually decides the behavior.
