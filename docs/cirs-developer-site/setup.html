Developer Setup

Set the API up in the right order.

The fastest path is also the safest one: install dependencies, prepare the database connection, choose the feature profile, then start the app with the matching environment values.

Primary command npm run dev

Use this only after the database connection, API keys, and active feature profile are aligned.

Default dev posture Local auth, app JWT, local TOTP

This is the safest working assumption when a machine is set up for day-to-day backend work instead of Supabase integration checks.

Main failure mode Wrong profile, missing governance env

Most startup confusion comes from mixing auth modes or skipping the production-only privacy and residency variables.

Production behavior Locked at build time

Setup Order

  1. Install dependencies.
  2. Prepare PostgreSQL access through DATABASE_URL and DIRECT_URL.
  3. Choose the feature profile before filling the rest of the env values.
  4. Set the required auth, MFA, and governance variables for that profile.
  5. Start locally with npm run dev or build with npm run build:production.
  6. Verify health, auth behavior, and the active profile after boot.

Baseline Requirements

  • Node.js and npm available locally
  • PostgreSQL connection for runtime and direct Prisma access
  • At least one API key through API_KEYS or API_KEY
  • Dashboard origin allowed through CORS_ORIGIN for real browser integration

Do not treat env setup as generic boilerplate. The profile choice changes which secrets and providers are actually required.

Development Mode

In development, the API reads FEATURE_* variables directly from the runtime environment. You can switch profiles by editing .env.development or by prefixing env values inline. 

npm install
npm run dev

Production Mode

In production, the feature profile is locked at build time. Runtime FEATURE_* values are ignored after npm run build:production. 

npm ci
npm run build:production
npm start

Startup fails closed in production when required security, breach-response, or residency variables are missing or unsafe.

Development Versus Production

Concern Development Production
Feature source Reads FEATURE_* directly from runtime env Uses the locked build-time profile
Profile switching Change .env.development or prefix env vars inline Rebuild with npm run build:production
Startup strictness Flexible for local work Fail-closed for missing or unsafe security and privacy settings
Typical command npm run dev npm start after a production build

Core Environment Values

Always needed

NODE_ENV, PORT, API_BASE_PATH, DATABASE_URL, DIRECT_URL, API_KEYS, CORS_ORIGIN.

Local auth profile

JWT_SECRET and MFA_ENCRYPTION_KEY are required when using app JWT and local TOTP.

Supabase profile

SUPABASE_URL, SUPABASE_ANON_KEY, and SUPABASE_SERVICE_ROLE_KEY become required.

Production governance

Privacy breach and data residency values are mandatory in production-safe deployments.

Environment Matrix

Variable group Main variables When required
Baseline runtime NODE_ENV, PORT, API_BASE_PATH, HOST, DATABASE_URL, DIRECT_URL, CORS_ORIGIN, TRUST_PROXY, API_KEYS All real deployments and almost all local work
Local auth JWT_SECRET, MFA_ENCRYPTION_KEY Required for app JWT plus local TOTP mode
Supabase auth SUPABASE_URL, SUPABASE_ANON_KEY, SUPABASE_SERVICE_ROLE_KEY Required when auth provider or token mode depends on Supabase
Password reset delivery PASSWORD_RESET_DELIVERY_WEBHOOK_URL Required in production-safe password reset flows
Privacy governance PRIVACY_DPO_CONTACT_EMAIL, PRIVACY_BREACH_PLAYBOOK_VERSION, PRIVACY_BREACH_NOTIFICATION_WINDOW_HOURS Required for production breach-response readiness
Data residency governance DATA_RESIDENCY_MODE, DATA_PROCESSOR_INVENTORY_VERSION, DATA_RESIDENCY_APPROVED_HOSTS Required in production when residency posture must be explicit
