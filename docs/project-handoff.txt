Project: Xypes CIRS API

Section 1: Backend Handoff Summary

Summary:
This is a TypeScript + Express REST API for a Citizen Incident Reporting System (CIRS). It exposes versioned endpoints under /api/v1, uses Prisma with PostgreSQL on Supabase, and now supports an incremental Supabase-auth rollout without breaking the legacy app-auth mode.

Current capabilities:
- Resource operations: citizens, agencies, responders, statuses, categories, severities, incidents, assignments, users, audit-logs
- Shared whitelist-based filtering, sorting, and pagination
- Centralized validation and error handling
- Role-based authorization with a capabilities endpoint
- Persistent audit logging for selected auth and mutation flows
- Swagger/OpenAPI docs in non-production
- Optional API key protection for non-auth versioned endpoints
- Rate limiting with standard headers
- Prisma-backed persistence across all controllers

Role model in the API:
- SYSTEM_ADMIN
- DEPARTMENT_MANAGER
- SUPERVISOR
- DISPATCHER
- RESPONDER
- CITIZEN_REPORTER
- AUDITOR

Role capability model:
- Capabilities are defined in src/types/auth.ts and exposed via GET /api/v1/users/capabilities.
- Dashboard code should rely on the backend capability payload for navigation and feature gating.
- Current scope labels are own, team, department, region, and global.
- Important: some scope labels are aspirational in the database layer today because the schema does not yet store enough department/region ownership metadata for true RLS enforcement.

Section 2: Authentication Modes

The backend now has three auth-related feature flags:
- SUPABASE_AUTH_ENABLED
- SUPABASE_JWT_ENABLED
- SUPABASE_TOTP_ENABLED

Mode 1: legacy app auth
- Email/password is validated locally.
- The backend issues its own JWT access token.
- The backend stores refresh tokens and auth sessions in auth_sessions.
- This remains the fallback when Supabase JWT mode is disabled.

Mode 2: Supabase email auth with app JWT fallback
- When SUPABASE_AUTH_ENABLED=true and SUPABASE_JWT_ENABLED=false, email/password identity is managed in Supabase Auth.
- The backend still returns the app JWT and uses the local auth_sessions refresh-token flow.
- Local users are linked to Supabase Auth through users.supabaseAuthUserId.

Mode 3: Supabase JWT mode
- When SUPABASE_JWT_ENABLED=true, login and refresh return Supabase accessToken and refreshToken.
- The backend accepts Supabase bearer tokens.
- Local user profile, role, and capability checks still come from the app database.
- In this mode, /auth/sessions and /auth/sessions/:id are intentionally not supported and return 501.

Supabase TOTP mode:
- When SUPABASE_TOTP_ENABLED=true, privileged-role MFA uses Supabase MFA/TOTP instead of the local encrypted TOTP secret flow.
- This mode requires SUPABASE_JWT_ENABLED=true.
- Privileged roles that require MFA are SYSTEM_ADMIN, DEPARTMENT_MANAGER, SUPERVISOR, and DISPATCHER.
- The backend checks Supabase Authenticator Assurance Level and rejects aal1 bearer tokens for privileged users with MFA enabled.

Required env values for Supabase modes:
- SUPABASE_URL
- SUPABASE_ANON_KEY
- SUPABASE_SERVICE_ROLE_KEY
- SUPABASE_AUTH_ENABLED
- SUPABASE_JWT_ENABLED
- SUPABASE_TOTP_ENABLED
- SUPABASE_AUTH_AUTO_CONFIRM_EMAIL
- SUPABASE_PASSWORD_RESET_REDIRECT_URL

Section 3: Dashboard Integration Contract

Public routes:
- POST /api/v1/auth/register
- POST /api/v1/auth/login
- POST /api/v1/auth/refresh
- POST /api/v1/auth/password-reset/request
- POST /api/v1/auth/password-reset/confirm
- GET /api/v1/health
- GET /api/v1/openapi.json
- GET /api/v1/docs

Protected auth routes:
- GET /api/v1/auth/me
- POST /api/v1/auth/logout
- GET /api/v1/auth/sessions
- DELETE /api/v1/auth/sessions/:id
- POST /api/v1/auth/mfa/setup
- POST /api/v1/auth/mfa/enable
- POST /api/v1/auth/mfa/disable

Token-handling rules for the dashboard:
- Always treat the auth response as mode-dependent.
- If Supabase JWT mode is enabled in the deployed backend, the dashboard should persist both accessToken and refreshToken from the backend auth response.
- The dashboard should use Authorization: Bearer <accessToken> on protected routes.
- The dashboard should call /auth/refresh with the current refreshToken when the access token expires.
- If the deployment is still on app-JWT mode, the response shape is compatible enough for the dashboard to keep using the backend-issued tokens without changing the request contract.

MFA/TOTP rules for the dashboard:
- Login still accepts an optional mfaCode field.
- In Supabase TOTP mode, /auth/mfa/setup, /auth/mfa/enable, and /auth/mfa/disable require the current refreshToken in the request body.
- /auth/mfa/setup returns TOTP bootstrap data including factorId, secret, otpauthUrl, and qrCode.
- /auth/mfa/enable may return an upgraded auth session bundle after successful verification.
- The dashboard must be prepared for a privileged user to authenticate successfully but still be blocked from protected resources until the MFA challenge upgrades the session to aal2.

Important integration boundaries:
- Dashboard pages for Supabase redirect handling such as `/auth/callback`, `/auth/confirm-email`, `/auth/error`, or a Supabase recovery page are frontend concerns and do not imply matching backend API routes.
- The current backend does not expose a Supabase auth webhook receiver or webhook-event log API for dashboard consumption unless such routes appear in active OpenAPI.
- Existing backend webhook integrations are outbound only: password reset delivery, security alert forwarding, and optional media scan submission.

API key note:
- Non-auth protected routes may still require x-api-key depending on deployment config.
- Browser dashboards should prefer a server-side proxy/BFF if API keys are enabled, rather than exposing keys directly in the browser.

Expected frontend behavior:
- Centralize API access in one typed client/service layer.
- Handle 401, 403, 404, 422, 429, and 501 explicitly.
- Use GET /api/v1/users/capabilities for feature gating instead of duplicating role logic everywhere in the UI.
- Keep refresh-token handling and logout logic centralized.
- Do not store audit data or sensitive tokens in localStorage unless there is a deliberate security review.

Section 4: Database and RLS Handoff

Current DB/auth linkage:
- Supabase remains the PostgreSQL host and now optionally provides Auth.
- App users are still stored in the local users table.
- Supabase-authenticated users are linked through users.supabaseAuthUserId.

Relevant SQL and schema files:
- prisma/schema.prisma
- prisma/reset-prisma-schema.sql
- prisma/add-supabase-auth.sql
- prisma/add-auth-sessions.sql
- prisma/add-password-reset-tokens.sql
- prisma/add-user-mfa.sql
- prisma/add-rls-policies.sql

RLS baseline:
- prisma/add-rls-policies.sql is a baseline Supabase/Postgres RLS script.
- It maps the current API role model to policies the database can safely enforce today.
- It includes helper functions that resolve the current app user and role from auth.uid().
- It restricts self-owned citizen and incident access where the schema supports it.
- It keeps sensitive auth tables API-only.

Important limitation:
- The current schema does not include department or region ownership fields on users, incidents, responders, or agencies in a way that RLS can use.
- That means department-scoped and region-scoped API permissions cannot yet be represented as strict database policies.
- If the role model changes later, create a new additive SQL migration rather than editing the already-applied baseline in production.

Section 6: Dashboard Build Guidance

Recommended integration approach:
- Use a single auth client abstraction that does not assume whether the backend is currently in app-JWT or Supabase-JWT mode.
- Store accessToken and refreshToken together and refresh centrally.
- Fetch /users/capabilities immediately after login or auth restoration.
- Gate admin, dispatch, audit-log, and MFA UI off backend capability and auth responses.
- Keep the UI ready for role and scope changes without hardcoding every rule in components.

Recommended near-term follow-up:
- Generate a typed API client from the OpenAPI spec.
- Add dashboard-side session restoration and automatic token refresh.
- Add a dedicated MFA screen for setup, challenge, enable, and disable.
- If true department/region scoping is required, extend the backend schema first and then revise the RLS migration.
